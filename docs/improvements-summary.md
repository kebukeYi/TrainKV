# TrainKV 改进总结(通俗版)

> 面向想快速了解"这轮做了什么、为什么做"的读者,不涉及代码细节。
> 详细技术版见 `improvements-detail.md`。

## 一句话总结

这轮工作分三件事:**让读写更快**(性能优化)、**修掉一批隐藏的 bug**(正确性修复)、**把没测过的链路补上测试**(测试建设)。最终五个核心链路——读、写、压缩、重启、vlog 垃圾回收——全部有端到端测试且通过并发检测(`-race`)验证。

---

## 一、性能:让读写更快

### 写路径:从"每次写都新建一堆临时对象"到"循环利用"

数据库写入时,每个操作都要在内存里建事务、建条目、算校验和。原来的代码每次都是"用完就扔",垃圾回收器忙个不停。优化思路是**能复用的都复用**:

- **事务池化**:以前每开一个事务,要新建 3 个对象;现在用完了放回池子,下一个事务直接捡现成的。
- **写通道不再每次开新协程**:以前每攒一批写入就启动一个新协程(类似每次叫一个外卖骑手),串行写入时纯属浪费;现在能自己写就自己写,忙不过来才叫协程。
- **标记条目复用**:每个事务提交时都要写一个"结束标记",以前每次新建,现在事务自带一个反复用。
- **编码零拷贝**:大 value 写进日志文件时,以前每次都要新建校验对象和临时缓冲,现在直接对已编码的数据一次性算校验和。
- **key 缓冲池**:给 key 加时间戳时要拷贝一份,以前每次新建,现在从池子里借、用完还。

### 读路径:从"每读一条都复制一遍"到"零复制扫描"

- **扫描不再逐条复制**:以前遍历数据时,每读一条都要把 key 和 value 各复制一份(一次扫描 10 万条 = 20 万次复制);现在迭代器自己管理稳定的缓冲区,扫描时**零分配**。
- **大 value 按需读取**:以前扫描时不管你要不要,先把每个 1MB 的大值都从磁盘拷进内存(扫 500 条 = 拷 500MB);现在只记下"值在哪",**你真正要读的时候才去取**。

### 效果数字

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 单条事务写入(分配次数) | 25 次/op | 14 次/op(-44%) |
| 并发写入(分配次数) | 18 次/op | 8 次/op(-56%) |
| 批量写入 10 条(分配次数) | 84 次/op | 64 次/op(-24%) |
| 1MB 大 value 写入(分配次数) | 14 次/op | 8 次/op(-43%) |
| 全表扫描 10 万条(分配次数) | 20 万次/op | 832 次/op(-99.6%) |
| SST 扫描 | —(此前不可测) | **0 次分配** |
| 大 value 扫描(500 条×1MB) | 每次必拷 528MB | 只搬 65KB,按需取值 |

## 二、正确性:修掉一批隐藏很深的 bug

### 最曲折的一个:"幽灵 key"之谜

**现象**:数据写入后,flush 到磁盘再读回来,约 1.4% 的 key 神秘消失,而且每次消失的 key 还不一样,像闹鬼。

**排查过程**(像侦探破案):
1. 直接解析磁盘文件 → 数据、索引、校验全是对的,key 明明在文件里;
2. 逐层调用链下探 → 表级查询能找到,数据库级查询却找不到;
3. 同一把 key 连查 5000 次 → 只有第一次失败;
4. 最终定位:**block 缓存**(内存里缓存磁盘块的那层)内部在做"热点晋升"时,把两个缓存条目的内容互换了,但查询逻辑还拿着旧的位置——于是 A 的查询拿到了 B 的缓存块。

**修复**:查询后重新确认条目位置。一行逻辑,但排查了整整一条调用链。

### 其他修掉的 bug(简述)

| Bug | 通俗解释 |
|---|---|
| 迭代器二次扫描返回空 | 扫完一遍再扫,啥都扫不出来(内部把迭代器弄丢了) |
| 压缩时偶发进程崩溃 | 并发压缩同一张表时,引用计数读法不对,可能把还在用的表删掉 |
| 关库后旧协程还在读 | 关闭数据库时只发"停止"信号不等人退出,立刻重开就会数据竞争 |
| 压缩统计协程泄漏 | 压缩产生的统计发送协程没人等它结束,会一直堵着 |
| L0→目标层压缩直接杀进程 | 判断逻辑用错了层级,多表压缩时触发致命断言 |
| 垃圾回收遇死数据就中止 | 压缩清掉旧版本后,GC 一遇到"查不到"的条目就整体失败,改成"查不到=已死,丢弃" |
| 三条压缩路径是"死代码" | L0→L0、末层→末层压缩因调度和条件矛盾,永远不会执行(已修复) |

### 一个重要的经验

**这些 bug 大多不是"读代码"读出来的,而是"写测试"测出来的**——端到端测试 + 并发检测(`-race`)把深埋的问题一个个逼了出来。
