## 〇、开场:项目介绍与动机

### Q1. 用一分钟介绍这个项目

**考察点**:表达结构、对项目全局的把握。

**参考答案**:
"TrainKV 是我参照 Badger 的设计、用纯 Go 从零实现的 LSM-Tree 键值存储引擎,核心约一万行、无 CGO。写入走 memtable(无锁跳表 + arena)+ WAL,刷盘成 L0–L6 分层 SSTable,由后台压缩归并;超过 1MB 的大 value 走 kv 分离,写进追加式 value log,LSM 里只留 12 字节指针。上层是 TSO 时间戳的 MVCC 事务,支持双哈希冲突检测;读路径有 W-TinyLFU 块缓存和布隆过滤器;崩溃恢复靠 WAL 重放 + MANIFEST 表登记。

这个项目我做了两类工作:一是功能——把事务、压缩、恢复、vlog GC 这些生产级关注点做完整;二是正确性和性能——以端到端测试加 -race 为纪律,修了 15 个以上深层缺陷,其中最有意思的是块缓存热点晋升交换导致 1.4% 的 key 静默丢失;性能上做了 8 项分配优化,并发写从 18 降到 8 allocs/op,扫描做到了零分配,大 value 改成惰性读取后扫 500 条 1MB 的数据搬运从 528MB 降到 65KB。"

**追问**:为什么不直接用/读 Badger 而要自己写?→ 见 Q3。这个项目最大的不足?→ 见 Q29。

### Q2. 项目的整体读写路径走一遍

**考察点**:架构全貌,能不能不看图讲清数据流。

**参考答案**:

写路径:
1. 用户 `txn.Set()` → entry 进事务的 pendingKeys(MVCC: key 上盖 startTs 时间戳);
2. `Commit()` → 先做冲突检测(若开启)→ 组装 `Request`(含 finTxn 结束标记)→ 发到 `writeCh`;
3. `handleWriteCh` 攒批:一次只允许一个批次在写,写完才取下一批(group commit,摊销 fsync);
4. 批内:大 value(> ValueThreshold=1MB)先追加进 vlog 并 sync(值先于引用落盘),LSM 侧条目换成 12B ValuePtr;然后 `LSM.Put` —— 追加 WAL + 插入活跃跳表;
5. 批全部落盘(或 WAL sync 完成)后,唤醒等待的提交者,返回 commitTs。

读路径:
1. 事务开启时等水位:所有 ≤ startTs 的提交都完成(commitMark),保证快照一致性;
2. `Get` 依次查:活跃 memtable → immutable memtable → L0 全部表(按 MaxVersion 逆序,新表优先)→ L1..L6 每层二分定位唯一可能命中的表;
3. 每张表先查布隆过滤器,不存在直接短路;存在则定位 block,先查 W-TinyLFU 块缓存,未命中才读盘;
4. 拿到 entry 后检查版本可见性(version ≤ startTs 才可见),大 value 条目按 ValuePtr 去 vlog mmap 里取。

**追问**:L0 为什么全部表都要查?→ 相邻 memtable 的 key 范围重叠,flush 不做归并,这是拿读放大换写路径简单(见 Q6)。mvcc 可见性在哪一层判断?→ LSM 层返回所有版本,事务迭代器按 startTs 过滤,压缩才物理删旧版本。

### Q3. 为什么不用现成的 Badger/RocksDB,要自己写一个?

**考察点**:动机是否真实、是否清楚自研的边界。

**参考答案**:
三个理由:第一,只有从零实现,才能把每个设计决策理解到能自己做的程度——为什么压缩分 level、为什么 kv 分离、为什么 vlog GC 要依赖压缩统计,这些读源码时是"知道",写的时候才变成"理解";第二,Badger 约 3 万行、RocksDB 30 万行,TrainKV 压到 1 万行,是能整库通读的完整实现,不是玩具——事务、GC、崩溃恢复、端到端测试都有;第三,纯 Go 无 CGO,单二进制部署,这个小生态里确实缺一个代码可读性优先的引擎。

同时我清楚它的定位:不与 RocksDB/Badger 正面竞争。我做过一份逐项对比(`docs/comparison.md`):TrainKV 没有数据压缩、没有列族、没有 range delete,压缩调度是 50s 定时器,零生产验证——这些是我主动列出的短板,也是接下来的演进方向。

**追问**:读 Badger 源码了吗?哪里不一样?→ 结构上是参照它的分层(kv 分离、MANIFEST、group commit),但实现是自己的;差异点:我的迭代器做了分块 arena 零分配扫描、大 value 惰性读取,分配优化更激进;另外我把三条压缩路径的死代码修活了,这类问题 Badger 靠长年生产迭代发现,我靠测试逼出来。

## 一、存储架构(简历 bullet 1)

### Q4. 为什么 memtable 用跳表?arena 分配器怎么工作?

**考察点**:内存表的数据结构选型、内存管理。

**参考答案**:
选跳表而非 B+树:① O(log n) 查找插入、无需再平衡;② 节点间是原子指针,读天然无锁,写用 CAS——本项目写路径被 writeCh 串行化、只有一个写者,但读可能来自任意协程,跳表正好适配"单写多读";③ 节点分配走 arena(一次大块分配、偏移量寻址),避免逐节点 malloc 的碎片和 GC 压力。

arena 实现:每个节点按随机高度分配,节点里只存 32 位 offset + size(前 32 位是 arena 内地址),key/value 也放 arena,通过偏移量取。整个 memtable 64MB 上限,写满转 immutable、新建一个,后台 flush 成 SST。

**追问**:跳表高度怎么定?→ 概率法(每层晋升概率约 1/2~1/4,封顶 MaxLevel),与 Redis zskiplist 同思路。arena 满了怎么办?→ memtable 达到 MemTableSize 就 rotation,不会让 arena 溢出。为什么不加锁读?→ 写者唯一、节点一旦写入不再原地修改(值更新是插新版本),读只需原子加载指针。

### Q5. SST 文件格式是什么?怎么定位一个 key?

**考察点**:磁盘数据结构的基本功。

**参考答案**:
SST 由 sstBuilder 顺序构建:entry 按 key+version 排序后,每 ~4KB(BlockSize)切一个 block;块尾记录 restart point 供二分;文件尾部是索引区——每个 block 的起始 key 偏移、handle、以及全表元数据(最大/最小 key、MaxVersion、StaleDataSize、布隆过滤器)。索引加载进内存,查 key 时:布隆过滤 → 二分索引定位 block → 读 block(优先块缓存)→ 块内二分。

**追问**:block 里怎么省内存?→ key 前缀压缩(restart point 处重置)。StaleDataSize 是干嘛的?→ 表内已死数据字节数,末层压缩用它判断"这张表值不值得单独重写回收"。布隆过滤器存哪?→ 索引区,随表元数据一起加载内存,查表前先过。

### Q6. L0 为什么允许 key 重叠?三层压缩路径分别什么时候触发?

**考察点**:LSM 分层设计的本质理解——这是简历"三条压缩路径"的直接追问。

**参考答案**:
L0 的表来自 memtable 直接倾倒,不同时刻写同一批 key,范围天然重叠;如果 flush 时强制归并,写路径就要多一次排序合并,所以用"L0 读放大(全部表都要查)换写路径简单"。代价是 L0 表数必须受限(NumLevelZeroTables=5),一超就压缩。L1 以下每层表范围互不重叠,每层只需一次二分。

三条压缩路径(50s ticker 调度,`pickCompactLevels` 按当前大小/目标大小打分):
1. **L0→目标层**:L0 得分 = 表数/5 ≥ 1(≥5 张表)→ 选重叠表归并到 base level,数据量小时直达 L6;
2. **L0→L0**:得分在 (0,1) 且攒了 ≥4 张小表(单表 < 2×fileSize[0]、表龄 ≥10s)→ 小表自合并,减少 L0 表数、降低读放大,又避免过早写穿下层;
3. **Lmax→Lmax(末层)**:末层某表 stale 数据 ≥10MB、表龄 ≥1h、MaxVersion ≤ discardTs → 只重写这一张表回收死数据,不牵连其他层。

**追问**:压缩怎么选表?→ L0 取全部重叠表(L0 按 MaxVersion 排序而非 fid,保证新版本先见);L1+ 取 key 范围重叠的表,与上层输入归并。压缩和写冲突怎么办?→ 压缩只动 immutable 数据,memtable 写入不受影响;表删除靠引用计数,被迭代器/读持有的表不会真删。你刚才说调度是 50s ticker——这是缺点吗?→ 是,压缩窗口大,写/读放大窗口随之变大,我把它列为第一改进项:事件驱动(写入量/水位触发)+ 参数化。

### Q7. 三个放大怎么算?你的设计里怎么权衡?

**考察点**:LSM 理论的落地程度。

**参考答案**:
- **写放大**:一个 key 从写入到稳态要经历 WAL → flush → 逐层压缩;7 层结构下最坏每层都重写一次。kv 分离实际上是在降写放大——压缩搬运的 LSM 条目只有 12B 指针,1MB 的 value 不跟着翻层。
- **读放大**:L0 全表数 + 每层 1 次二分;布隆过滤器把"不存在的 key"在每层短路,块缓存把热 block 留在内存,这俩是读放大的两道闸。
- **空间放大**:旧版本和删除标记到压缩才物理清除;MVCC 下受 NumVersionsToKeep=1 + discardTs 控制(见 Q10),末层靠 stale 统计定向回收。

压缩的本质是拿写放大换读放大和空间放大;kv 分离和布隆是这个三角里的两个校正项。

**追问**:kv 分离的代价?→ 读大 value 多一次 vlog 访问(+指针解引用);vlog 有自己的空间放大,要靠 GC 回收,而 GC 的死数据统计完全依赖压缩时"哪些版本被丢了"——所以 GC 有效性和压缩调度强耦合,这也是我把压缩调度列为第一改进的另一个原因。

## 二、事务与 MVCC(简历 bullet 2)

### Q8. startTs / commitTs 怎么分配?读事务为什么要"等水位"?

**考察点**:TSO MVCC 的可见性语义,简历"TSO 时间戳 MVCC 事务"的直接追问。

**参考答案**:
TransactionManager 维护全局 `nextTxnTs`(tsLock 保护):写事务提交时 `commitTs = nextTxnTs` 并自增——时间戳即全局提交序,由单点分配保证可比较。读事务 `startTs = nextTxnTs - 1`,开启时调 `commitMark.WaitForIndexDone(startTs)`:阻塞到所有 ≤ startTs 的事务都提交完成。

为什么必须等:读事务的可见性规则是"version ≤ startTs 可见"。提交序与时间戳序一致(分配即排序),等水位就等价于"我开启时,所有比我早的事务都已落盘",不会读到半提交状态。写事务是懒等待(ensureStartTsReady,首次读 LSM 才等)——纯写事务不付这笔延迟。

水位由两个 LimitMark 维护:`commitMark` 记录提交完成进度(供读等待),`startMark` 记录还有谁在读(供压缩判断旧版本能否删,见 Q10)。LimitMark 内部是 begin/done 事件队列 + 后台协程推进 doneIndex。

**追问**:读事务会饿死吗?→ 不会,水位单调推进,写侧提交完成就 Done,等待者按序唤醒。没有中心点行不行?→ 分布式下 TSO 要换成 HLC/时钟方案(Percolator/TiDB 思路),这是我能讲清楚为什么单机用全局计数器的原因。

### Q9. 冲突检测怎么做的?为什么要"双哈希"?

**考察点**:乐观并发控制细节,简历"双哈希冲突检测"的直接追问。

**参考答案**:
`DetectConflicts=true` 时是乐观并发控制:写事务每次 Set 把 key 的两个独立哈希(MemHash + xxhash)登记进 `conflictKeys`,每次 Get 把 MemHash 记入 `readKeys`。提交时 `hasConflict`:遍历"startTs 之后提交的事务"的写 key 哈希快照,只要命中本事务的 readKeys 就返回 ErrConflict,由用户重试。

双哈希的原因:写侧登记、读侧比对的是 64 位哈希而非原 key——省内存,但单哈希有碰撞概率,两个互相独立的哈希同时碰撞概率可忽略,把误报(假冲突)压到工程上为零。选择"误报"而非"漏报"是刻意的:冲突检测宁可错杀,不能放过。

**追问**:已提交事务的写集合怎么维护?→ 提交时把 conflictKeys 拷成 `[]uint64` 快照挂进 commitedTxns(按 commitTs 索引),超出水位的事务整体淘汰;这也是我池化事务对象的前提——原来 map 被 commitedTxns 引用着,池化会复用正在被检查的内存,改成快照后 map 才能安全归还(见 Q19 追问)。写多读少场景开销?→ DetectConflicts 可关,关掉后退化为"最后提交者赢",隔离性交给用户。

### Q10. 压缩为什么只能删 version ≤ discardTs 的旧版本?

**考察点**:MVCC 与 GC 的交互,面试高频陷阱题。

**参考答案**:
MVCC 的承诺:任何 startTs=T 的读事务必须能看到它应该看到的版本。假设某 key 有 v5、v3 两个版本,读事务 T=4 正在读 v3;若压缩"只留最新"把 v3 删了,T 读不到本该看见的数据——历史被篡改。

所以删除条件是"这个版本不可能再有活跃读者需要它":`discardTs` = startMark 的完成水位 = 已结束读事务的最高 startTs。版本 version ≤ discardTs 意味着任何新开启的读事务 startTs > version,看不见它;而看见了它的事务都已结束。压缩归并时,对同一 key 保留最新 NumVersionsToKeep(=1)个版本,更旧且 ≤ discardTs 的直接丢弃。

**追问**:discardTs 落后很多怎么办?→ 长事务会卡水位,旧版本堆积——这是所有 MVCC 引擎的共同问题(PostgreSQL vacuum、TiDB GC safe point 同款),我的 LimitMark 结构上和它们的 watermark 是一类东西,区别只在单机没有事务超时强制回滚,后续可以加。

### Q11. 迭代器的 MVCC 可见性和"读己之写"怎么实现?

**考察点**:事务栈的整体串联。

**参考答案**:
事务迭代器 = 事务未提交缓冲(pendingKeys,读己之写)+ LSM 合并迭代器的双层结构。LSM 层 MergingIterator 用最小堆归并所有来源(memtable、各层 SST),同一个 key 的多个版本按 (key, version) 序相邻输出;事务层按 startTs 过滤:取第一个 version ≤ startTs 的版本,若 meta 是删除标记则该 key 视为不存在跳到下一个 key。

读己之写:pendingKeys 与 LSM 输出归并,同 key 时 pending 版本(自己的 startTs)优先——事务内写了立刻能读到。

**追问**:并发压缩时迭代器会崩吗?→ 迭代器对涉及表 IncrRef,压缩的 DecrRef 用 atomic 返回值判零——这里我修过一个 bug:原来 AddInt32 之后用普通读 `ref == 0` 判断,并行压缩同时减计数时可能提前删掉还被引用的表(见 Q23)。

## 三、读路径(简历 bullet 3)

### Q12. W-TinyLFU 块缓存的原理?你的实现里有哪些部件?

**考察点**:缓存算法,简历"W-TinyLFU 块缓存"的直接追问,必须有图级别的描述能力。

**参考答案**:
W-TinyLFU 解决的问题是:LRU 对"偶发的全量扫描"没有抵抗力——一次性扫过全表会把所有热数据冲出缓存。W-TinyLFU 用**访问频率**(而非最近性)做准入,让新条目必须证明自己的频率才能挤掉老条目。

四个部件(每个分片一套):
1. **窗口 LRU(占 15%)**:新条目先进窗口,给"刚写入、频率还是 1"的条目一个观察期,不被立刻淘汰,也吸收突发访问;
2. **分段 LRU(占 85%)**:窗口满则按频率准入——从窗口淘汰的条目,频率够高才进 SLRU 的 probation 段(15%);probation 段条目再次被访问,与 protected 段(85%)末尾比频率,赢了才晋升 protected;protected 满了降级回 probation;
3. **CM-Sketch(Count-Min Sketch,计数器数 = 条目数×2)**:频率的近似计数,4 位计数器、对数直方图增减,防扫描把频次刷爆;
4. **Doorkeeper 布隆(误判率 0.5%)**:从没见过的新 key 直接记布隆不进 sketch——扫描流量(每个 key 只见一次)根本不占计数器,这是抗扫描的关键一层。

**追问**:为什么块缓存用 W-TinyLFU 而不是 LRU?→ SST 块访问的"偶发扫描"模式非常典型(比如分析型查询扫一层),LRU 会被冲垮;Caffeine/RocksDB 的实践都是频率缓存。CM-Sketch 会不会计数溢出/偏大?→ 会偏大(碰撞),所以配对数衰减定期减半;偏大的后果只是"新条目更难准入",安全方向。淘汰粒度?→ 按 block(4KB),不是按表。

### Q13. 块缓存为什么要分 16 个分片?路由哈希为什么用乘法散列?

**考察点**:并发优化 + 细节真实性(能答出这题说明缓存是自己写的)。

**参考答案**:
块缓存每次访问(命中也要做 LRU 晋升、准入统计,会改状态)都要拿写锁。全局单锁在压缩协程与读协程并发时退化为 futex 竞争——profile 显示锁竞争约占读路径 13%。分片 16 份(2^4)后每把锁流量降为 1/16,竞争基本消除,这是缓存分片那轮优化的直接动机。

路由有个细节:缓存 key 是 `fid<<32 | blockIdx` 的结构化数值,直接取低位当分片号会集中在少数分片(blockIdx 低位分布不均)。我用乘法散列:hash × 黄金比例常数 0x9E3779B97F4A7C15,取高 4 位做分片号——乘法把高位信息搅进结果,分布均匀。

**追问**:为什么不用 RWMutex?→ 读多写少场景 RWMutex 看似合适,但"命中也要晋升"意味着每次读都是写操作,RLock 没意义。分片数为什么是 16?→ 2 的幂便于位运算取模;默认 CacheNums=10240,每分片 640 条,太小会增加哈希冲突、太大锁粒度不够,10K 量级下 16 是经验平衡点。

### Q14. 讲讲你排查"幽灵 key" bug 的过程。(重点故事题)

**考察点**:调试方法论、讲故事能力——这是整套面试材料里最值得讲透的一个故事。

**参考答案**:
现象:`TestFlushReadIntegrity` 里 flush 后读回 10 万个 key,约 1.4% 的 key 查不到;诡异的是每次运行消失的 key 都不一样,像闹鬼。

排查过程分四步:
1. **排除磁盘层**:直接解析 SST 文件——数据、块索引、布隆、CRC 全部正确,key 明明在文件里。排除构建和持久化。
2. **二分调用链**:表级 `Table.Search` 能找到,数据库级 `Get` 找不到 → 问题夹在中间:块缓存。
3. **复现规律**:同一把 key 连查 5000 次,只有第一次失败,后面全命中——指向"某次状态变化后缓存给错东西",而非数据本身错。
4. **定位根因**:W-TinyLFU 的分段 LRU 做"热点晋升"时,会把 probation 段和 protected 段的两个 `list.Element` 的 storeItem 内容交换(`*bitem, *item = *item, *bitem`)。交换后这两个块对应的 key→element 映射变了,但 `Cache.get` 返回的是交换**前**查到的 element 引用——key A 的查询拿到 key B 的缓存块。布隆过滤/索引都拦不住,因为缓存命中根本不查盘。

修复只有一行逻辑:`Cache.get` 在晋升等 stage 操作完成后,重新从 map 解析 element。但排查走完了整条调用链。我为此写了回归测试:10 万 key flush 后全量读回,0 丢失,进 CI。

这个 bug 给我两个教训:一是"读写都正确"的组件组合起来未必正确——交换本身是合法的缓存内部操作,错在把中间态引用泄漏给了调用方;二是幽灵级别的 bug 靠读代码很难发现,是靠"每次丢的 key 都不一样"这类**规律观察**加上分层二分逼出来的。

**追问**:为什么是 1.4% 不是更多?→ 只有"恰好被晋升操作波及的两个相邻段条目"才错,晋升频率低、命中是随机的,所以比例小且不稳定。这类错误对用户意味着什么?→ 静默数据错误,比崩溃严重得多——这也是我后来坚持"读回完整性"类端到端测试的原因。为什么单测没抓住?→ 缓存单测不涉及"晋升+查询交错"的时序,必须用数据量把晋升挤出来。

### Q15. 零分配扫描是怎么做到的?从 20 万次分配到 832 次的路径是什么?

**考察点**:内存优化 + Go 运行时理解,简历"-99.6%"的直接追问。

**参考答案**:
原来的实现:合并迭代器每输出一个 key,就把 key 和 value 各 SafeCopy 一份给上层——扫 10 万条 = 20 万次小对象分配,GC 压力全在读路径上。

三步改造:
1. **合并层去拷贝**:MergingIterator.Item() 直接返回子迭代器的 Item,不再逐 key 复制;
2. **稳定内存**:去拷贝的前提是子迭代器返回的内存"活得够久"。memtable 侧设计了 ChunkedArena——64KB 分块,块一旦分配**永不移动、永不回收**,返回的切片永久有效(SST 侧天然满足:key 进迭代器私有 arena,value 是 mmap 视图,表在内存就在);活跃 memtable 有一层 copyItems 模式——它可能被并发写导致 arena 重新分配,所以对它仍用副本,immutable/flush 后的表用视图;
3. **契约化回收**:迭代器 Rewind 时统一重置 arena,把上一轮的内存整体还给下一轮用——10 万条数据的扫描只需几百个 64KB 块轮转。剩余 832 次来自首次索引装载和堆初始化,属于一次性开销。

效果:memtable 扫描 20 万 → 832 次,SST 扫描 0 分配。代价是**借用语义**:Item 只在下次 Next/Rewind 前有效——我在 README 里把它写成显式使用契约,和 Badger 对 Item 的处理一致。

**追问**:为什么不让 GC 解决?→ 可以,但 20 万次分配意味着读路径自己制造 GC 周期,尾延迟由 GC 决定,存储引擎的读 P99 不能交给 GC。ChunkedArena 为什么不分一块大的?→ 大块要预判扫描总量,且 Rewind 一次性归还大块会瞬时内存尖峰;分块按需增长、轮转复用。escape analysis 在哪里用?→ `-gcflags='-m'` 验证 Item 不逃逸、CRC digest 不逃逸等,是写路径优化的取证工具(见 Q21)。

### Q16. 大 value 惰性读取的 API 为什么这么设计?用户写错了会怎样?

**考察点**:API 设计权衡 + 契约意识,简历"528MB→65KB"的直接追问。

**参考答案**:
动机:kv 分离后,扫描遇到 vlog 条目,旧实现每次 `Item()` 都把 1MB value 从 mmap 拷出来——扫 500 条 = 528MB 拷贝,哪怕用户只看 key。改成:`TxnIterator` 对 BitValuePointer 条目只记录 12B 的 ValuePtr 位置,`Item.Value()` 被调用时才解码指针、从 vlog mmap 读并 SafeCopy——用户真正要的才付钱。效果:500×1MB 扫描搬运量 528MB → 65KB(只剩 LSM 侧元数据),耗时 ~110µs。

契约设计:Value() 结果在下一次 Next 前有效(借用语义的一部分);README 明确写了三条契约(事务不可复用、Item 借用、大 value 用 Value())。为什么不做自动拷贝的"安全模式"?——接口里留了 IsSetCache 之类的开关,但拷贝与否本质是性能取舍,引擎不应该替用户做决定,Badger 同样是 Value([]byte) 显式取。

**追问**:vlog 那次读在热路径上,慢吗?→ mmap 视图 + SafeCopy 只拷实际 value 长度;页缓存命中后是内存拷贝级别。GC 重写文件时迭代器正拿着 ValuePtr 怎么办?→ vlog GC 三层保护(见 Q27):文件 RWMutex、活跃迭代器计数(文件挂到 FilesToDel 延后删)、GC 重写走同一写通道。

### Q17. 布隆过滤器怎么实现的?参数怎么定?

**考察点**:基础数据结构的实现细节。

**参考答案**:
标准位数组 + k 个哈希,这里两个用途:① SST 级布隆——存在表元数据里,查表前短路"肯定不存在",直接省掉二分和可能的读盘,是读放大的第一道闸;② 缓存 doorkeeper 布隆——记录"见过哪些 key",误判率 0.5%,吸收扫描流量。

参数:预期条目数与误判率定 m/k;SST 侧按 key 数构造,构建期一次性写入索引区。工程点:哈希复用 Get 的哈希计算,不重复算;误判率的取舍——调高省内存但放行的无效读变多,4KB block 的读代价低,所以可以选相对宽松的参数。

**追问**:为什么不用 cuckoo filter?→ 布隆够用且实现小、无删除需求;cuckoo 的优势(可删除)在只读 SST 里用不上。

## 四、写路径(简历 bullet 4)

### Q18. group commit 的完整流程?

**考察点**:写路径并发模型。

**参考答案**:
目标:fsync 是 4ms 量级,一条一 sync 吞吐封死在 ~250/s。做法:所有写事务的 Request 进 `writeCh`,唯一的 `handleWriteCh` 攒批——一批内所有条目一次性写 vlog/WAL、一次 sync、一起返回。并发事务越多,单次 fsync 摊到的条目越多,这是写吞吐随并发提升的原因(串行 4ms/op,4 并发 2.1ms/op)。

实现细节:批处理用令牌(blockChan)防止并发多批;空闲时当前协程直接写(不开新协程),忙时才派发;批次切片 `reqs[:0]` 复用底层数组。

**追问**:为什么不用 mmap+WAL 组合减少 sync?→ sync 语义不能省,该优化的是"几次 sync"。这个模型的风险?→ 单写者串行,写吞吐上限 = fsync 频率 × 批大小;要再上量得做 pipeline(WAL 组提交与 memtable 写并行)——在 todo 里。

### Q19. 8 项写路径优化分别是什么?(简历"8 项分配优化"必被追问)

**考察点**:优化是系统工程不是玄学——逐条讲清"现象 → 定位 → 改法"。

**参考答案**(pprof alloc_objects 指路,每项都有明确归属):

| # | 优化 | 改前问题 | 改法 |
|---|---|---|---|
| 1 | handleWriteCh 内联写 | 每批起一个 ~2KB 栈的协程 + 批切片 make | 令牌空闲时当前协程直接写,忙时才派协程;`reqs[:0]` 复用 |
| 2 | 事务池化 | NewTransaction 3 次分配(占 profile 34.6%) | db.txnPool 复用 Transaction;前提是 #4 |
| 3 | finTxn 标记复用 | 每次提交 NewEntry + strconv.AppendUint 2 次分配 | 池化事务内嵌 finEntry + finTsBuf 复用 |
| 4 | conflictKeys 快照化 | map 被 commitedTxns 长期引用,无法池化 | 提交时拷成 []uint64 快照,hasConflict 线性扫描,map 归池 |
| 5 | EncodeEntry 单次 CRC | crc32.New 的 digest 逃逸 + MultiWriter 致缓冲逃逸 | 先编码进 buf,对结果一次性 crc32.Checksum |
| 6 | ValuePtr 值切片 | `append(req.ValPtr, &p)` 局部变量逃逸 | `[]*ValuePtr` → `[]ValuePtr` |
| 7 | ValuePtr 编码 scratch | 每次 Encode make([]byte,12) | 请求级私有缓冲,首次增长后 0 分配 |
| 8 | key 缓冲池 | 每条 entry 一次 key+8 时间戳拷贝 | KeyTsBufPool 池化 *[]byte |

整体效果:单条 25→14、并发 18→8、批量 84→64、1MB 大 value 14→8 allocs/op。

**追问**:为什么 #4 是 #2 的前提?→ 详述见 Q9 追问。哪项收益最大?→ 事务池化(34.6% profile 占比),但它必须最后做才安全——先解决引用问题。

### Q20. 你踩过什么优化的坑?

**考察点**:诚实度 + 实战深度。答案就藏在自己的 profile 数据里。

**参考答案**:
key 缓冲池第一版池化 `[]byte`,`sync.Pool.Put` 的 interface 装箱把事情搞砸了:24 字节的 slice header 放不进 pool 的单字 data 槽,每次 Put/Get 都装箱分配——profile 显示 Discard 里冒出 43,691 次分配,净亏损。改成池化 `*[]byte`(指针能放进单字槽,缓冲在盒内增长)后变成净收益。教训:**池化的对象本身不能有分配**,存指针不存结构,存完必须用 profile 验收而不是想当然。

**追问**:怎么发现的?→ 优化后重新采 alloc profile,发现优化点自己变成了新的分配热点——这也是我坚持"每项优化单独验收"的原因。

### Q21. 为什么你用 allocs/op 评判写性能,而不是 ns/op?

**考察点**:基准测试方法论。

**参考答案**:
三个原因:① 写路径 ns/op 被 fsync 主导,本机 WSL2 上同一基准噪声从 2.6ms 到 38ms,不可比;fsync 优化空间在 OS/硬件层,不在我的代码里;② allocs/op 是确定性指标,方差极小,且本轮优化的对象就是分配;③ B/op 会被 arena 预分配摊销污染——b.N 不同预分配摊到的份额不同,跨运行不可比。

方法论:pprof alloc_objects 找热点(注意小对象采样偏差)→ 改 → `-benchmem -count=3` 取中位数验收 → `-gcflags='-m'` 逃逸分析取证。SyncWrites=true 是生产配置下的口径,另有 no-sync 口径(~3.2µs/op)衡量纯代码路径。

**追问**:为什么 count=3 取中位数?→ 尾部受偶发调度影响,中位数稳健;benchtime=2s 保证 b.N 够大摊热身。

## 五、正确性:bug 排查与测试(简历 bullet 5)

### Q22. "三条压缩路径死代码"是怎么回事?你怎么发现的?

**考察点**:代码审查能力 + 系统性思维——简历里最"内行"的一条。

**参考答案**:
做压缩测试时发现:三个设计好的压缩路径(L0→L0、L0→Lmax、末层自合并)在真实运行里永远不会触发,写多少数据都走不到。逐条查下来是四处互相独立的缺陷,每个都把路径掐死在不同环节:

1. **调度层过滤**:pickCompactLevels 只保留 score ≥ 1.0 的层——而 L0→L0 恰恰是"表数 < 5(score<1)"时的路径,被调度器整体排除;修复:L0 恒参与调度,由路径内部条件(≥4 张小表)把关;
2. **统计未持久化**:sstBuilder 的 buildBlockIndex 从没把 staleDataSize 写进表索引 → 所有表的 stale 恒为 0 → 末层压缩"stale ≥ 10MB"的第一步就返回 false;修复:写进索引;
3. **删除标记进不了末层**:标记的保留条件 hasOverlap 在 nextNext ≥ MaxLevelNum 时恒 false → 所有进入 L6 的压缩都顺手把标记丢了 → 末层永远没有 stale 可回收(和 #2 构成连环死锁);修复:末层压缩显式保留标记,由 Lmax→Lmax 统一回收;
4. **大表选中却不压缩**:findMaxLevelTables 里 `t.Size() >= needFileSize` 时 break 落到 `return false`——注释写"找到就返回",实现却是放弃;修复:登记压缩状态后 return true。

体会:这四个 bug 单看每一处都"合理"——条件都写了、分支都有,坏在**组合**:调度器假设路径自洽,路径假设统计正确,统计假设标记在。没有一条是靠读代码读出来的,全是写端到端测试(强制构造 4 张小表/45 万条删除标记/10MB stale)逼出来的。这也是我后来把"每条设计路径必须有对应的触发测试"当纪律的原因。

**追问**:怎么验证修复后路径真的会走?→ 三个专用测试:TestCompactionL0ToL0(4 表→1)、TestCompactionL0ToLmax(5 表直达 L6)、TestLastLevelCompaction(45 万标记、10MB stale),断言不只看结果,还看层级结构变化。

### Q23. 除了死代码,还有哪些有代表性的 bug?

## 六、崩溃恢复与 vlog GC

### Q25. 崩溃恢复的完整流程?MANIFEST 崩溃窗口为什么安全?

**考察点**:持久化正确性的推理能力。

**参考答案**:
恢复 = WAL 重放 + MANIFEST 对账:
1. 读 MANIFEST,重建"表→层级"结构(每个 SST 的登记);
2. 找出未 flush 的 WAL,`recovery2SkipList` 重放进 memtable;
3. WAL 解析规则:每条记录带 CRC32;事务条目带 BitTxn 标记,事务尾有 finTxn 标记(key = `!train!txn!fin`,value 是 commitTs)——恢复时收集同事务条目、校验 finTxn 的事务号与 commitTs 一致才整批入跳表;不一致 → ErrBadTxn,截断到最后有效偏移;
4. 尾部撕裂写:读到 EOF/UnexpectedEOF/CRC 错且其后全零 → 判定是断电残尾,回退并截断——半个事务不会出现,因为 finTxn 是事务原子的分界。

MANIFEST 崩溃窗口(为什么"先写 MANIFEST 再挂表"不丢数据):
- **窗口 A**:SST 文件写完、MANIFEST 未写 → 重启时这份 SST 是"孤儿",不在登记里,被忽略;数据仍在 WAL 里(删 WAL 的条件是 fid ≤ 最大 SST fid)→ 重放,不丢;
- **窗口 B**:MANIFEST 写了、内存层级没挂上 / WAL 还没删 → 重启按 MANIFEST 恢复,WAL 里 fid 更小的被正常丢弃(数据已在 SST)→ 不重复;
两个方向的窗口都收敛到"宁可重放,不可丢失"。

**追问**:删除 WAL 的时机?→ flush 完成后按 fid 判定,顺序保证不早删。MANIFEST 自身损坏?→ 定期 rewrite 成全量快照,单条损坏回退上一份;这是我做得很浅的地方,主动承认。

### Q26. 为什么 vlog 必须先于 WAL sync?顺序错了会怎样?

**考察点**:崩溃一致性的因果推理。

**参考答案**:
LSM 里大 value 条目只存 12B 指针。若 WAL(含指针)先 sync、vlog 还没落盘,断电后恢复:WAL 重放出"指针指向 Fid/Offset"的条目,但那个位置是未持久化的垃圾——悬垂引用,读回错误数据,而且是静默的。

所以顺序固定:写 vlog → **sync vlog** → 写 WAL → sync WAL。"值先于引用"是 kv 分离架构下崩溃一致性的核心约束,和文件系统"先写数据块再写 inode"同构。

**追问**:两次 sync 不浪费?→ 是 group commit 攒批后的两次批级 sync,批越大摊销越好;这是 kv 分离为崩溃安全付的固定成本。vlog 写大 value 的优化?→ EncodeEntry 单次 CRC(先编码后校验)+ 增量 sync,消掉了双拷贝(B/op 从 12,820 降到 115)。

### Q27. vlog GC 全链路怎么走?discard 统计从哪来?

**考察点**:kv 分离架构特有的子系统,简历"vlog GC"的追问。

**参考答案**:
死数据从哪来:压缩丢弃旧版本时,若被丢版本的值是 ValuePtr,累计 `discardStats[vp.Fid] += vp.Len`,经 FlushCh 汇入文件级统计。`RunValueLogGC(ratio)`:按"丢弃量/文件大小"挑文件(超 ratio 才值得重写)→ `gcReWriteLog`:遍历旧文件每个条目,拿 key+version 回查 LSM——**版本还在**说明是活数据,重写进当前 vlog 文件并更新 LSM 指针;**查不到**(被压缩清了)说明是死数据,直接丢弃——这里我修过一个 bug:原实现查不到就报错中止整次 GC,而"查不到=已死"才是正确语义。

**追问**:GC 与并发读怎么共存?三层保护:① vlog 文件 RWMutex——读持 RLock,GC 删除持 Lock;② 活跃迭代器计数——文件还被迭代器用就挂到 FilesToDel 延后删;③ 写路径单写者,GC 的重写也走同一写通道,不会与正常写交错。GC 期间这个文件还能写吗?→ 不能,重写目标是当前活跃文件,旧文件只读,天然无冲突。

## 七、对比、软肋与延伸

### Q28. 和 Badger 的技术差异是什么?

**考察点**:是否真读过参照对象,能不能客观。

**参考答案**:
相同骨架:kv 分离、MANIFEST、group commit、TSO MVCC 的整体分层一致——这是刻意的,参照成熟设计降低"发明错误"的风险。差异三点:
1. **分配策略我更激进**:Badger 的迭代器仍逐 Item 拷贝,我做了 ChunkedArena 零分配扫描和大 value 惰性读(SST 扫描 0 allocs/op);
2. **并发写模型**:Badger 多写者、我单写者 group commit——简单但吞吐上限低,是我承认的取舍;
3. **成熟度差距**:Badger 有数据压缩(zstd/snappy)、多年生产验证;我没有压缩、零生产部署,靠测试纪律补一部分正确性信心。
这些差异都记录在 `docs/comparison.md`,包括我没有的能力清单。

**追问**:那 TrainKV 的适用场景?→ 中小规模嵌入式 Go 场景、纯 Go 单二进制、代码可读性优先——对标 goleveldb 的生态位。

### Q29. 你项目最大的缺点是什么?(必考,主动暴露 + 计划)

**考察点**:自我认知、工程判断——这个问题答得好是加分,回避是减分。

**参考答案**(按严重度排序):
1. **压缩调度是 50s ticker**——最大架构弱点:压缩窗口大,写/读放大窗口随之变大,且 vlog GC 统计依赖压缩,GC 有效性也受拖累。计划:事件驱动(写入量/水位触发)+ 阈值参数化;
2. **无数据压缩**:裸存,磁盘占用高。计划:block 级 Zstd,边界已留好(builder 收口处);
3. **零生产验证 + 无 A/B 基准**:没有和 goleveldb/Badger 同机对比;计划补;
4. **崩溃恢复测试浅**:只有 WAL 尾部损坏,flush/压缩/GC 中途断电的深场景未覆盖;计划:注入式故障测试。

最后补一句定调:这些都在 `docs/comparison.md` 和 todo 里白纸黑字,是我做完对比分析后自己列的——我认为知道自己引擎的边界,和知道它怎么工作同样重要。

### Q30. 如果要把它做成分布式,你会怎么改?

**考察点**:向上延伸的思考(常作为压轴题)。

**参考答案**(分层答):
- **复制**:单机 WAL 换 Raft group(WriteRequest 本来就是批接口,log 就是 Raft entry,group commit 模型能平移);
- **分片**:按 key range 分片(和 LSM 的层级结构天然配合,元数据服务管理 range→replica 映射);
- **事务**:单分片沿用 TSO;跨分片要么中心化 TSO(TiDB 路线),要么 Percolator 式两阶段;我的冲突检测双哈希可以跨节点比对;
- **压缩/GC**:变成每 replica 独立执行,Raft 保证幂等;discard 统计按分片聚合;
- **难点前置**:MVCC 水位(LimitMark)在多节点下变成全局 safe point 推进问题——需要租约/心跳确认"没有事务还持有旧快照",这是 TiDB GC 的已知难题,我会先读它们的方案再动手。

**追问**:现在的代码哪些能直接复用?→ 存储层全部(LSM/vlog/缓存/MVCC 版本管理),事务管理器的时间戳分配要抽象成接口,水位推进逻辑要改造成可插拔。

## 附:高频"快问快答"清单(面试前 30 分钟过一遍)

| 问题 | 一句话答案 |
|---|---|
| 写路径最坏延迟? | fsync 主导,~4ms/op(SyncWrites=true);no-sync ~3.2µs |
| 并发写吞吐为什么比串行好? | group commit,一次 fsync 摊多个事务(4ms → 2.1ms/op) |

| 大 value 读在哪一步? | 只在 item.Value() 调用时;扫描只搬 12B 指针 |
| 版本什么时候物理删除? | 压缩时,保留最新 1 个版本,且 version ≤ discardTs |
| discardTs 是什么? | 已结束读事务的最高 startTs(startMark 水位) |
| 幽灵 key 根因? | W-TinyLFU 晋升交换 element 内容后返回旧引用,一行修复 |
| 缓存几把锁? | 16 分片 × 各 1 把;命中也要晋升所以是写锁 |
| 崩溃后最多丢什么? | 未 sync 的事务(原子性由 finTxn 保证,不会出现半个事务) |
| vlog 和 WAL 的 sync 顺序? | vlog 先(值先于引用落盘) |
| 三条压缩路径? | L0→目标层(≥5 表)、L0→L0(≥4 小表且 score<1)、Lmax→Lmax(stale≥10MB) |
| 最大短板? | 50s ticker 压缩调度;其次无数据压缩、零生产验证 |
