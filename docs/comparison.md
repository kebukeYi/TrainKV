# TrainKV 与主流 LSM-KV 产品对比

> 对比对象:LevelDB、RocksDB、Badger(及 Go 生态的 goleveldb)。

## 一、横向对比总览

| 维度 | **TrainKV** | **LevelDB** | **RocksDB** | **Badger** |
|---|---|---|---|---|
| 语言/依赖 | 纯 Go,无 CGO | C++ | C++(Go 侧需绑定) | 纯 Go |
| 代码规模 | ~1 万行 | ~1.5 万行 | 30 万+ 行 | ~3 万行 |
| 事务 | ✅ MVCC(TSO)+ 冲突检测 | ❌ 仅批量原子性 | ✅ 悲观/乐观事务 | ✅ MVCC + 冲突检测 |
| value 日志分离 | ✅ | ❌ | ❌(BlobDB 实验) | ✅ |
| 压缩(compression) | ❌ 无 | ✅ Snappy | ✅ Snappy/Zstd/LZ4 | ✅ zstd/snappy |
| 块缓存 | ✅ W-TinyLFU | ✅ LRU | ✅ 多级 | ✅ LRU |
| 布隆过滤器 | ✅ | ✅(前缀) | ✅(每层/前缀) | ✅ |
| 列族/多 memtable | ❌ | ❌ | ✅ | ❌ |
| Range Delete / Merge Op | ❌ | ❌ | ✅ | ✅(部分) |
| 压缩调度 | 50s ticker(偏慢) | 写触发 + 后台线程 | 事件驱动 + 多线程 | 后台 compact + 触发器 |
| 配置面 | 简单 | 简单 | 数百项 | 适中 |
| 生产部署验证 | ❌ 无 | ✅ 海量 | ✅ 海量 | ✅ 中等规模 |

## 二、TrainKV 的优点

1. **学习价值**:~1 万行、无 CGO、组件齐全(跳表+arena、W-TinyLFU、LSM 压缩、MVCC、vlog GC、MANIFEST 恢复),是"一门课讲完 LSM 全栈"的教学级完整实现;
2. **分配开销极低**:写路径 5-8 allocs/op、扫描零分配、大 value 惰性读;
3. **功能完备度对中小规模足够**:Badger 的核心能力均有端到端测试;
4. **测试纪律**:五链路端到端 + `-race` 全绿;
5. **部署友好**:纯 Go 单二进制,无 CGO 工具链依赖。

## 三、TrainKV 的缺点

1. **零生产验证**:无部署、无 fuzz/混沌测试、崩溃恢复仅浅场景、无与同类产品的 A/B 基准;
2. **压缩调度慢**(架构级):50s ticker,写放大/读放大窗口大;
3. **功能缺口**:无数据压缩、无列族、无 range delete、无 merge operator、无写限速;
4. **并发模型简单**:写通道单写者串行化,写吞吐受限于单写协程与串行 fsync;
5. **契约心智负担**:事务不可复用、迭代器借用语义、大 value 惰性读(`Value()`)需使用者注意;
6. **vlog GC 依赖压缩统计**:GC 有效性与压缩调度强耦合。

## 四、定位建议

- **不应与 RocksDB/Badger 正面竞争**;
- 正确定位:**教学/学习型完整 LSM 实现 + 中小规模嵌入式 Go 场景的可用引擎**;
- 对标对象是 **goleveldb**(Go 生态同类嵌入式选择);
- 若目标生产可用,优先级:压缩调度参数化 → 数据压缩 → 崩溃恢复深场景 → A/B 基准;
- 若目标学习,建议保持"可读性优先"约束,避免向 RocksDB 式复杂度演进。
